# 流式对话系统分布式限流面试讲解

---

## 一、分布式限流基础概念

### 1.1 什么是分布式限流

**分布式限流**是指在分布式系统环境下，通过限制某个时间窗口内的请求数量或并发数，保护系统资源不被耗尽的机制。

**核心三要素**：

| 要素 | 说明 |
|------|------|
| **资源** | 保护的对象（API、服务、数据库连接等） |
| **阈值** | 允许的最大数量（QPS、并发数、字节数等） |
| **时间窗口** | 限流的时间范围（秒级、分钟级等） |

### 1.2 为什么流式对话场景需要限流

| 传统 HTTP 请求 | SSE 流式对话 |
|----------------|--------------|
| 请求-响应模式，一次请求一次响应 | 长连接模式，一次连接持续推送 |
| 响应时间短，线程占用时间短 | 响应时间不确定（几秒到几十秒） |
| 容易估算并发量 | 并发量与连接时长成正比 |
| 拒绝直接返回 429 | 拒绝需要优雅发送事件 |

**流式对话的特殊风险**：

1. **并发难以预估**：每个请求可能持续几十秒，并发数 = QPS × 平均响应时间
2. **模型成本高**：AI 模型调用是稀缺资源，超负载会导致整体降级
3. **长连接资源**：HTTP 连接、文件描述符、内存等持续占用
4. **用户体验敏感**：排队超时需要友好提示，不能直接断开

## 二、流式对话的特殊限流挑战

### 2.1 挑战一：长连接保持 vs 线程释放

**问题**：

```
传统方案：
┌─────────────────────────────────┐
│ 请求 → Tomcat 线程处理 → 等待    │
│ 模型响应 → 发送 → 线程释放        │
│                                 │
│ 如果响应 30 秒，线程阻塞 30 秒    │
│ 100 个请求 → 100 个线程被占用    │
└─────────────────────────────────┘
```

**解决方案**：

- 使用 `SseEmitter` 异步返回
- Tomcat 线程立即释放，业务逻辑在独立线程池执行
- 排队等待由 Scheduler 轮询 + 事件驱动实现

### 2.2 挑战二：实时响应要求 vs 排队等待

**问题**：

- 用户期望低延迟响应
- 系统需要排队保护资源
- 排队时间过长会导致用户体验差

**解决方案**：

- **双机制等待**：定时轮询（保底）+ 事件驱动（加速）
- **超时机制**：最大等待时间（如 20 秒），超时发送 REJECT 事件
- **优雅拒绝**：拒绝时发送完整 SSE 事件流，保持用户体验

### 2.3 挑战三：动态消息长度 vs 固定窗口

**问题**：

- 不同问题的回答长度差异大（一句话 vs 长文档）
- 简单的 QPS 限流不够公平（短回答消耗少，长回答消耗多）
- 需要同时限制 **并发数** 和 **请求频率**

**解决方案**：

| 限流维度 | 指标 | 作用 |
|----------|------|------|
| **并发数** | 同时处理的请求数 | 保护模型资源 |
| **排队超时** | 最大等待时间 | 防止无限等待 |
| **许可过期** | 兜底释放时间 | 防止资源泄漏 |
| **幂等校验** | 同一用户同时只能一个请求 | 防止用户重复提交 |

### 2.4 挑战四：分布式环境下的一致性

**问题**：

- 多实例部署，需要全局一致的限流
- 某个实例崩溃，排队中的请求需要自动清理
- 跨实例的通知唤醒机制

**解决方案**：

- 基于 Redis 的分布式数据结构
- 存活标记 TTL 自动过期
- Redis Pub/Sub 跨实例通知

## 三、常用限流算法对比

### 3.1 限流算法概览

| 算法 | 核心思想 | 优点 | 缺点 | 适用场景 |
|------|----------|------|------|----------|
| **固定窗口** | 时间切片计数 | 简单易实现 | 边界"突刺"问题 | 简单场景 |
| **滑动窗口** | 窗口平滑移动 | 精确限流 | 实现复杂，存储成本高 | 精确限流要求高 |
| **漏桶** | 恒定速率出水 | 流量整形，削峰填谷 | 无法应对突发流量 | 需要匀速处理 |
| **令牌桶** | 匀速生成令牌 | 支持突发流量 | 需要独立令牌生成 | 允许一定突发 |
| **信号量** | 并发槽位控制 | 精确控制并发 | 需要配合排队 | 并发限制 |

### 3.2 各算法在流式对话中的适用性分析

#### 3.2.1 固定窗口计数器

```
时间线:    [0-1s]  [1-2s]  [2-3s]
计数:        100      50     200
            ↓        ↓       ↓
          通过     通过    拒绝
```

**问题**：边界突刺

```
0.9s 时来了 100 个请求（通过）
1.1s 时又来了 100 个请求（也通过）
→ 0.9s-1.1s 这 0.2s 内实际通过了 200 个请求
```

**流式对话适用性**：❌ 不适合

- 流式请求持续时间长，窗口边界问题更严重
- 可能导致某一时刻并发远超阈值

#### 3.2.2 滑动窗口

```
时间线:    [0.0-1.0s]  [0.1-1.1s]  [0.2-1.2s]
计数:        100          95           90
```

**实现**：记录每个请求的时间戳，计算当前窗口内的数量

**流式对话适用性**：⚠️ 部分适合

- 精确，但存储成本高（每个请求需要记录时间戳）
- 流式请求持续时间长，需要记录的时间跨度大
- 更适合短请求的精确 QPS 限制

#### 3.2.3 漏桶算法

```
请求流入 → [漏桶] → 恒定速率流出
           ↓
         溢出的请求被丢弃
```

**特点**：

- 出口速率恒定，平滑流量
- 突发流量会被丢弃或排队

**流式对话适用性**：❌ 不适合

- 模型调用无法匀速处理（响应时间差异大）
- 排队等待需要通知机制，漏桶不友好
- 用户体验差（不知道要等多久）

#### 3.2.4 令牌桶算法

```
令牌生成器: 每秒生成 100 个令牌

请求:
  请求 A → 拿 1 个令牌 → 通过
  请求 B → 拿 1 个令牌 → 通过
  请求 C → 无令牌 → 等待/拒绝
```

**特点**：

- 支持突发流量（令牌有积累时）
- 控制的是 **请求速率**（QPS）

**流式对话适用性**：⚠️ 部分适合

- 适合控制请求频率
- 但流式对话更关注 **并发数**（持续占用资源）
- 可以配合并发控制使用

#### 3.2.5 信号量 + 排队队列

```
信号量: [P1][P2][P3]  (3 个并发槽位)

排队队列: [请求 A][请求 B][请求 C][请求 D]
          ↑
        队头优先

流程:
  1. 请求入队
  2. 检查是否在队头窗口内
  3. 尝试获取信号量
  4. 成功 → 执行业务
  5. 失败 → 等待下次机会
```

**特点**：

- 精确控制 **并发数**（同时处理的请求数）
- 配合队列实现 **公平排队**（FIFO）
- 支持 **事件驱动** + **定时轮询** 双重等待机制

**流式对话适用性**：✅ 最适合

| 优势 | 说明 |
|------|------|
| **并发控制精确** | 直接限制同时处理的请求数，保护模型资源 |
| **公平排队** | ZSet + 自增 score 保证 FIFO |
| **非阻塞等待** | Tomcat 线程立即释放，排队由独立机制处理 |
| **优雅降级** | 排队超时发送拒绝事件，保持用户体验 |
| **分布式支持** | 基于 Redis，多实例一致 |

### 3.3 算法选择建议

| 场景 | 推荐算法 | 理由 |
|------|----------|------|
| **流式对话** | 信号量 + 排队队列 | 并发控制、公平排队、非阻塞 |
| **API 网关 QPS 限制** | 滑动窗口 | 精确限流 |
| **消息队列消费** | 漏桶 | 流量整形 |
| **允许突发的 API** | 令牌桶 | 支持突发 |
| **数据库连接池** | 信号量 | 并发控制 |

### 4.2 核心组件详解

#### 4.2.1 中心化限流服务（Redis）

**为什么用 Redis**：

| 特性 | 说明 |
|------|------|
| **分布式一致性** | 多实例共享同一状态 |
| **丰富数据结构** | Semaphore、ZSet、Bucket、Topic 开箱即用 |
| **高性能** | 单线程模型，内存操作 |
| **原子性** | Lua 脚本保证多操作原子性 |
| **自动过期** | TTL 防止僵尸条目 |

**使用的数据结构**：

```java
// 1. 信号量：控制并发
RPermitExpirableSemaphore sem = redissonClient.getPermitExpirableSemaphore("rag:global:chat:semaphore");
sem.tryAcquire(0, 600, TimeUnit.SECONDS);  // 0 等待，600 秒自动过期

// 2. ZSet：公平排队
RScoredSortedSet<String> queue = redissonClient.getScoredSortedSet("rag:global:chat:queue");
queue.add(nextQueueSeq(), requestId);  // score = 自增序号

// 3. Bucket：存活标记
RBucket<String> entry = redissonClient.getBucket("rag:global:chat:entry:" + requestId);
entry.set("1", Duration.ofMillis(ttlMillis));  // 带 TTL

// 4. Topic：事件通知
RTopic topic = redissonClient.getTopic("rag:global:chat:queue:notify");
topic.publish("permit_changed");
```

#### 4.2.2 Lua 脚本原子性

**为什么需要 Lua**：

```
不使用 Lua 的问题（竞态条件）：

线程 A: ZRANGE 取队头 → 发现 requestId 是自己
线程 B: ZRANGE 取队头 → 也发现 requestId 是自己
线程 A: ZREM 移除
线程 B: ZREM 移除（此时已不在队列）
线程 A: 尝试 acquire permit
线程 B: 尝试 acquire permit
→ 两个请求都认为自己是队头，可能导致超出并发限制
```

**Lua 解决方案**：

```lua
-- queue_claim_atomic.lua
-- 一次往返完成：检查窗口 + 清理僵尸 + 出队

local headEntries = redis.call('ZRANGE', queueKey, 0, maxRank + slack - 1)

local liveRank = -1
local liveCount = 0
for i = 1, #headEntries do
    if redis.call('EXISTS', entryPrefix .. member) == 1 then
        if member == requestId then
            liveRank = liveCount
        end
        liveCount = liveCount + 1
    else
        redis.call('ZREM', queueKey, member)  -- 清理僵尸
    end
end

if liveRank < 0 or liveRank >= maxRank then
    return {0}  -- 不在窗口内
end

redis.call('ZREM', queueKey, requestId)  -- 原子出队
return {1, score}
```

#### 4.2.3 熔断降级机制

**降级策略**：

| 策略 | 触发条件 | 处理方式 |
|------|----------|----------|
| **排队超时** | 等待时间 > maxWaitSeconds | 发送 REJECT 事件，记录会话 |
| **SSE 断开** | emitter.onCompletion/onTimeout/onError | 自动取消排队，释放资源 |
| **线程池拒绝** | chatEntryExecutor 满负荷 | 降级为 timeout 拒绝路径 |
| **限流开关** | 配置关闭 | 跳过限流，直接执行 |

**优雅拒绝示例**：

```java
private void handleReject(String question, String conversationId, SseEmitter emitter) {
    // 1. 记录拒绝消息到会话历史
    RejectedContext context = recordRejectedConversation(question, conversationId, userId);
    
    // 2. 发送完整 SSE 事件
    SseEmitterSender sender = new SseEmitterSender(emitter);
    sender.sendEvent(SSEEventType.META.value(), new MetaPayload(...));
    sender.sendEvent(SSEEventType.REJECT.value(), 
        new MessageDelta("response", "系统繁忙，请稍后再试"));
    sender.sendEvent(SSEEventType.FINISH.value(), new CompletionPayload(...));
    sender.sendEvent(SSEEventType.DONE.value(), "[DONE]");
    sender.complete();
}
```

#### 4.2.4 线程池配合

**独立的执行线程池**：

```java
@Bean
public Executor chatEntryExecutor(RAGRateLimitProperties rateLimitProperties) {
    int size = rateLimitProperties.getGlobalMaxConcurrent();  // 与并发数对齐
    return new ThreadPoolExecutor(
            size, size, 60, TimeUnit.SECONDS,
            new SynchronousQueue<>(),           // 无缓冲
            new ThreadPoolExecutor.AbortPolicy() // 超出直接拒绝
    );
}
```

**为什么这样设计**：

| 设计点 | 原因 |
|--------|------|
| 核心/最大线程数 = maxConcurrent | 双重保险，Redis 信号量 + 线程池 |
| SynchronousQueue | 无缓冲，超出立即拒绝 |
| AbortPolicy | 拒绝策略明确，不降级到 callerRuns |

## 五、实际应用案例与最佳实践

### 5.1 案例：Ragent 流式对话限流

#### 架构设计

```
RAGChatController.chat()
    │
    ├── 创建 SseEmitter
    └── RAGChatServiceImpl.streamChat()
            │
            └── ChatQueueLimiter.enqueue()
                    │
                    ├── 限流关闭? ── YES ──→ chatEntryExecutor.execute()
                    │
                    └── 限流开启
                            │
                            └── FairDistributedRateLimiter.acquire()
                                    │
                                    ├── setEntryMarker (TTL)
                                    ├── ZSet 入队
                                    ├── tryAcquireIfReady
                                    │       ├── 成功 → grant → 执行业务
                                    │       └── 失败 → scheduleQueuePoll
                                    │
                                    └── 等待: 轮询(200ms) + Topic 通知
                                            │
                                            ├── 超时 → onTimeout → REJECT
                                            ├── 取消 → cleanup
                                            └── 成功 → grant
```

#### 关键配置

```yaml
rag:
  rate-limit:
    global:
      enabled: true           # 启用限流
      max-concurrent: 50      # 最大并发数
      max-wait-seconds: 20    # 排队超时时间
      lease-seconds: 600      # permit 兜底过期
      poll-interval-ms: 200   # 轮询间隔
```

### 5.2 最佳实践清单

#### 5.2.1 设计原则

| 原则 | 说明 |
|------|------|
| **非阻塞** | 不阻塞 Tomcat 线程，排队由独立机制处理 |
| **可观测** | 限流日志、指标监控、拒绝统计 |
| **可降级** | 支持动态开关、超时拒绝、手动释放 |
| **防泄漏** | 多重兜底：try/finally、TTL 过期、SSE 生命周期绑定 |
| **公平性** | FIFO 排队，队头优先 |

#### 5.2.2 实现要点

**1. 正确释放资源**

```java
// 错误做法：忘记释放
String permitId = sem.tryAcquire();
doBusiness();  // 异常 → permit 泄漏

// 正确做法：try/finally
String permitId = sem.tryAcquire();
try {
    doBusiness();
} finally {
    sem.release(permitId);
}
```

**2. 正确处理竞态条件**

```java
// 错误：先检查再操作（竞态窗口）
if (sem.availablePermits() > 0) {
    String permitId = sem.tryAcquire();  // 可能还是失败
}

// 正确：使用 Lua 保证原子性
// 或直接 tryAcquire，用返回值判断
String permitId = sem.tryAcquire();
if (permitId != null) {
    // 成功
}
```

**3. 绑定生命周期**

```java
// 绑定 SSE 生命周期，连接断开自动取消
cancelBinder -> {
    emitter.onCompletion(cancel);
    emitter.onTimeout(cancel);
    emitter.onError(e -> cancel.run());
}
```

#### 5.2.3 监控与告警

建议监控的指标：

| 指标 | 说明 | 告警阈值 |
|------|------|----------|
| `limiter.queue.size` | 排队队列长度 | > 100 |
| `limiter.queue.wait_time_p99` | 排队等待时间 P99 | > 5s |
| `limiter.reject.rate` | 拒绝率 | > 10% |
| `limiter.permit.available` | 可用许可数 | 持续为 0 |
| `limiter.permit.lease_expired` | 过期释放计数 | > 0（说明有泄漏） |

## 六、常见面试问题及参考答案

### Q1: 为什么流式对话场景需要限流？不能直接用 Tomcat 线程池控制吗？

**参考答案**：

> 流式对话和传统 HTTP 请求有本质区别：
>
> 1. **持续时间长**：一个请求可能持续几十秒，如果用 Tomcat 线程阻塞等待，100 个请求就会占满线程池
> 2. **资源消耗大**：AI 模型调用是稀缺资源，需要精确控制并发
> 3. **长连接资源**：HTTP 连接、文件描述符等持续占用
> 4. **用户体验**：排队超时需要友好提示，不能直接断开
>
> Tomcat 线程池是第一道防线，但不够：
> - 无法实现分布式全局一致
> - 无法实现公平排队
> - 无法优雅拒绝（发送 SSE 事件）
>
> 所以需要专门的分布式限流机制。

---

### Q2: 为什么用信号量 + ZSet 而不是令牌桶或漏桶？

**参考答案**：

> 这是由流式对话的特点决定的：
>
> **令牌桶/漏桶的问题**：
> - 控制的是 **请求速率（QPS）**，而流式对话更关注 **并发数**
> - 漏桶不支持排队等待的通知机制
> - 用户不知道要等多久，体验差
>
> **信号量 + ZSet 的优势**：
> 1. **并发控制精确**：信号量直接控制同时处理的请求数，保护模型资源
> 2. **公平排队**：ZSet + 自增 score 保证 FIFO，先到先得
> 3. **非阻塞等待**：Tomcat 线程立即释放，排队由轮询 + 事件驱动处理
> 4. **优雅降级**：排队超时可以发送拒绝事件，保持用户体验
> 5. **分布式支持**：基于 Redis，多实例一致
>
> 简单说：**令牌桶适合限制"来多少"，信号量适合限制"同时处理多少"**，流式对话更关心后者。

---

### Q3: 排队等待会不会阻塞 Tomcat 线程？为什么？

**参考答案**：

> **不会阻塞。** 原因如下：
>
> **调用链分析**：
> ```java
> Controller.chat() {
>     SseEmitter emitter = new SseEmitter();
>     service.streamChat(emitter);  // 这个方法不阻塞！
>     return emitter;  // 立即返回！
> }
> 
> service.streamChat() {
>     limiter.acquire(request);  // 只是写入 Redis + 注册任务，不等待！
>     // 立即返回！
> }
> 
> limiter.acquire() {
>     queue.add(requestId);       // Redis 操作，很快
>     scheduleQueuePoll(ticket);  // 只是注册定时任务，不等待
>     return;  // 立即返回！
> }
> ```
>
> **关键设计**：
> 1. **`acquire()` 是非阻塞的**：只是做几次 Redis 操作，然后返回
> 2. **业务逻辑是回调**：`onAcquired` 封装成 Runnable，拿到许可后在线程池中执行
> 3. **SseEmitter 的异步机制**：Spring MVC 对 SseEmitter 有特殊处理，返回后 Tomcat 线程释放，但 HTTP 连接通过 AsyncContext 保持
>
> **排队期间的线程状态**：
> - Tomcat 线程：已释放，回到线程池
> - 业务执行线程：未启动（等待 permit）
> - 轮询线程：Scheduler 定时检查
> - HTTP 连接：保持打开（等待 SSE 事件）

### Q4: 如何保证分布式环境下的限流一致性？

**参考答案**：

> 通过 **Redis 中心化存储** + **Lua 原子脚本** 保证：
>
> **1. 中心化存储**：
> - 信号量：`RPermitExpirableSemaphore`，所有实例共享同一信号量
> - 排队队列：`RScoredSortedSet`，所有实例的请求入同一队列
> - 存活标记：`RBucket` 带 TTL，防止 JVM 崩溃导致僵尸
>
> **2. Lua 原子脚本**：
> ```lua
> -- 一次原子操作完成：
> -- 1. ZRANGE 取队头窗口
> -- 2. EXISTS 检查存活（清理僵尸）
> -- 3. ZREM 出队
> -- 4. 返回结果
> ```
> 避免了"先检查后操作"的竞态条件。
>
> **3. 跨实例通知**：
> - Redis `RTopic` Pub/Sub 机制
> - 一个实例释放 permit，发布通知
> - 所有实例的 `PollNotifier` 收到通知，唤醒等待者
>
> **4. 防泄漏兜底**：
> - Permit 有 `leaseSeconds` 自动过期
> - 存活标记有 TTL
> - SSE 生命周期绑定，连接断开自动取消

### Q5: 如何处理限流拒绝？用户体验如何保证？

**参考答案**：

> 限流拒绝不是简单的断开连接，而是**优雅降级**：
>
> **1. 完整的 SSE 事件流**：
> ```
> META:   {conversationId, taskId}
> REJECT: {type: "response", delta: "系统繁忙，请稍后再试"}
> FINISH: {messageId, title}
> DONE:   [DONE]
> ```
> 前端可以正常展示拒绝消息。
>
> **2. 记录会话历史**：
> - 用户的问题和拒绝消息都会写入对话历史
> - 用户可以看到自己问了什么，得到了什么回复
> - 新会话还会生成标题
>
> **3. 限流开关**：
> - 配置 `rag.rate-limit.global.enabled` 可动态关闭
> - 紧急情况可以降级
>
> **4. 排队超时配置**：
> - `max-wait-seconds` 控制最大等待时间
> - 不会让用户无限等待

### Q6: 多实例部署时，一个实例崩溃了，排队中的请求怎么办？

**参考答案**：

> 通过 **TTL 自动过期机制** 处理：
>
> **问题场景**：
> ```
> 实例 A: 请求 A 入队，score=1001
> 实例 A: JVM 崩溃
> ZSet:   [A(1001), B(1002), C(1003)]
> 问题:   A 永远排在队头，但实际已失效
> ```
>
> **解决方案**：
>
> **步骤 1：入队前设置存活标记**
> ```java
> setEntryMarker(requestId, maxWaitMillis + 5s_buffer);
> // Redis: SET entry:{requestId} "1" EX 25s
> ```
>
> **步骤 2：Lua 检查时清理僵尸**
> ```lua
> for i = 1, #headEntries do
>     if redis.call('EXISTS', entryPrefix .. member) == 1 then
>         -- 存活，计数
>     else
>         -- 不存在（TTL 过期或被删除），ZREM 清理
>         redis.call('ZREM', queueKey, member)
>     end
> end
> ```
>
> **步骤 3：Permit 兜底释放**
> ```java
> sem.tryAcquire(0, 600, TimeUnit.SECONDS);
> // 600 秒后即使没显式释放，也会自动过期
> ```
>
> **总结**：
> - 存活标记 TTL：JVM 崩溃后自动过期
> - Lua 脚本：检查时自动清理僵尸
> - Permit 过期：防止资源永久泄漏

### Q7: 如何监控限流效果？有哪些关键指标？

**参考答案**：

> 建议监控以下指标：
>
> **1. 队列状态**：
> - `limiter.queue.size`：当前排队数量 → 告警：> 100
> - `limiter.queue.wait_time_p50/p95/p99`：排队等待时间 → 告警：P99 > 5s
>
> **2. 拒绝情况**：
> - `limiter.reject.count`：拒绝次数
> - `limiter.reject.rate`：拒绝率 → 告警：> 10%
> - `limiter.reject.timeout_count`：超时拒绝次数
> - `limiter.reject.cancel_count`：取消拒绝次数
>
> **3. 许可使用**：
> - `limiter.permit.total`：总许可数
> - `limiter.permit.available`：可用许可数 → 告警：持续为 0
> - `limiter.permit.lease_expired`：过期释放数 → 告警：> 0（说明有泄漏）
>
> **4. 业务指标**：
> - `limiter.acquire.latency`：获取许可耗时
> - `limiter.acquire.success_rate`：获取成功率
>
> **日志建议**：
> - 排队开始/结束日志
> - 拒绝原因日志（超时/取消/线程池拒绝）
> - 异常情况日志（Permit 过期释放等）

### Q8: 限流和幂等是什么关系？这个项目中怎么配合的？

**参考答案**：

> **限流**和**幂等**是两个不同的概念，但可以配合使用：
>
> | 概念 | 作用 | 关注点 |
> |------|------|--------|
> | **限流** | 保护系统不被打垮 | "能处理多少" |
> | **幂等** | 防止重复提交 | "重复请求怎么办" |
>
> **本项目中的配合**：
>
> **Controller 层的幂等校验**：
> ```java
> @IdempotentSubmit(
>     key = "T(...UserContext).getUserId()",
>     message = "当前会话处理中，请稍后再发起新的对话"
> )
> @GetMapping("/rag/v3/chat")
> public SseEmitter chat(...)
> ```
> 同一用户同时只能有一个请求在处理（基于 userId 做幂等）。
>
> **Service 层的全局限流**：
> ```java
> chatQueueLimiter.enqueue(question, conversationId, emitter, onAcquire);
> ```
> 全局控制最大并发数（默认 50）。
>
> **配合效果**：
> 1. 先过幂等：同一用户不能重复提交
> 2. 再过分局限流：防止某一个用户占满所有并发
> 3. 最后过全局限流：保护整体系统
>
> 两层防护：用户级别 + 系统级别。

## 七、面试话术总结

### 7.1 开场介绍（1 分钟版）

> "分布式限流在流式对话场景中非常关键。和传统 HTTP 请求不同，流式对话的请求持续时间长，模型调用是稀缺资源，所以需要精确控制并发数，同时保证用户体验。
>
> 我们采用 **Redis 信号量 + ZSet 公平排队** 的方案。信号量控制同时处理的请求数，ZSet 保证先到先得的公平性。为了不阻塞 Tomcat 线程，我们用 **定时轮询 + Redis Pub/Sub 事件驱动** 的双重等待机制，排队期间 Tomcat 线程立即释放。
>
> 还有很多细节需要考虑，比如 JVM 崩溃后的僵尸清理（用 TTL 存活标记）、优雅拒绝（发送完整 SSE 事件）、多实例通知（Redis Topic）等。"

### 7.2 核心要点记忆清单

| 要点 | 关键词 |
|------|--------|
| **为什么限流** | 长连接、模型稀缺、并发难预估 |
| **用什么算法** | 信号量 + ZSet 排队（不是令牌桶/漏桶） |
| **为什么不阻塞** | Tomcat 线程立即释放，SseEmitter 异步 |
| **怎么等待** | 200ms 轮询 + Topic 事件驱动 |
| **怎么保证公平** | ZSet + 自增 score，Lua 原子判断 |
| **怎么防泄漏** | try/finally、TTL、SSE 生命周期绑定、Permit 过期 |
| **怎么优雅拒绝** | META → REJECT → FINISH → DONE 完整事件流 |
| **分布式一致性** | Redis 中心化 + Lua 原子性 + Topic 跨实例通知 |

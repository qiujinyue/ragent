# 对话记忆模块实现分析

## 概述

对话记忆模块是 Ragent RAG 系统的核心组件之一，负责管理用户对话历史，支持长对话场景下的上下文理解。该模块采用**混合记忆架构**：保留最近几轮原始对话 + 对历史对话进行摘要压缩，在保证对话连贯性的同时控制上下文窗口大小。

### 1.2 存储层实现：JdbcConversationMemoryStore

**核心职责**：管理对话历史消息的持久化存储

```java
public class JdbcConversationMemoryStore implements ConversationMemoryStore {
    // 加载历史：按配置的轮数限制查询
    public List<ChatMessage> loadHistory(String conversationId, String userId) {
        int maxMessages = memoryProperties.getHistoryKeepTurns() * 2;  // user+assistant 为一轮
        List<ConversationMessageVO> dbMessages = conversationMessageService.listMessages(
                conversationId, userId, maxMessages, ConversationMessageOrder.DESC);
        // ... 转换为 ChatMessage 并过滤
    }
    
    // 追加消息：同时更新会话元信息
    public String append(String conversationId, String userId, ChatMessage message) {
        ConversationMessageBO conversationMessage = ConversationMessageBO.builder()
                .conversationId(conversationId)
                .userId(userId)
                .role(message.getRole().name().toLowerCase())
                .content(message.getContent())
                .build();
        String messageId = conversationMessageService.addMessage(conversationMessage);
        
        // 用户消息时更新会话最后时间
        if (message.getRole() == ChatMessage.Role.USER) {
            conversationService.createOrUpdate(conversation);
        }
        return messageId;
    }
}
```

**过滤规则**：
- 只保留 `USER` 和 `ASSISTANT` 角色的消息
- 确保历史以用户消息开头（`normalizeHistory`）
- 去除空内容消息

## 二、记忆触发时机

### 2.1 记忆加载时机

在对话流水线的**第一个阶段**触发：

```java
// StreamChatPipeline.java
private void loadMemory(StreamChatContext ctx) {
    List<ChatMessage> history = memoryService.loadAndAppend(
            ctx.getConversationId(),
            ctx.getUserId(),
            ChatMessage.user(ctx.getQuestion())  // 当前问题先写入
    );
    ctx.setHistory(history);
}
```

**时序**：用户发起对话请求 → 进入流水线 → `loadMemory()` → 并行加载摘要+历史 → 合并结果

### 2.2 记忆追加时机

每次调用 `loadAndAppend()` 时，会先加载历史，再将当前问题追加到存储：

```java
// ConversationMemoryService.java
default List<ChatMessage> loadAndAppend(String conversationId, String userId, ChatMessage message) {
    List<ChatMessage> history = load(conversationId, userId);  // 先加载
    append(conversationId, userId, message);  // 再追加
    return history;  // 返回追加前的历史（不含当前消息）
}
```

**关键设计**：返回的历史不包含当前追加的消息，避免重复。

### 2.3 响应消息的落库时机

在 `StreamChatEventHandler.onComplete()` 中完成：

```java
// 响应结束时，将 assistant 消息写入记忆
public void onComplete(String thinkingContent, Long thinkingDuration) {
    ChatMessage assistantMessage = ChatMessage.assistant(responseBuffer.toString());
    assistantMessage.setThinkingContent(thinkingContent);
    assistantMessage.setThinkingDuration(thinkingDuration);
    
    // 写入记忆存储
    memoryService.append(conversationId, userId, assistantMessage);
}
```

## 三、记忆压缩触发机制

### 3.1 触发条件

| 条件 | 配置项 | 默认值 | 说明 |
|------|--------|--------|------|
| 摘要开关 | `summary-enabled` | `true` | 全局控制是否启用压缩 |
| 消息角色 | - | `ASSISTANT` | 只在助手回复后触发 |
| 轮数阈值 | `summary-start-turns` | `5` | 用户消息数达到此值开始压缩 |

### 3.2 完整压缩流程

```
┌─────────────────────────────────────────────────────────────────────────┐
│                    compressIfNeeded() 入口                              │
│  ├─ summaryEnabled == false? → return                                 │
│  ├─ message.role != ASSISTANT? → return                               │
│  └─ CompletableFuture.runAsync(doCompressIfNeeded, executor)          │
└────────────────────────────┬────────────────────────────────────────────┘
                             ▼
┌─────────────────────────────────────────────────────────────────────────┐
│                   doCompressIfNeeded() 异步执行                         │
│  ├─ Redisson tryLock() 抢分布式锁                                      │
│  │   └─ 抢锁失败 → return                                            │
│  ├─ countUserMessages() 统计用户消息数                                 │
│  │   └─ total < summaryStartTurns → return                            │
│  ├─ 计算摘要区间 [afterId, cutoffId]                                   │
│  ├─ 增量检查：afterId >= cutoffId → return（无新增需摘要内容）          │
│  ├─ listMessagesBetweenIds() 获取待摘要消息                            │
│  ├─ summarizeMessages() 调用 LLM 生成摘要                              │
│  └─ createSummary() 持久化摘要                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

### 3.3 增量摘要算法

**核心思想**：只对新增消息做摘要，避免重复计算

```java
private void doCompressIfNeeded(String conversationId, String userId) {
    // 1. 获取最新 N 轮用户消息（倒序）
    List<ConversationMessageDO> latestUserTurns = conversationGroupService
            .listLatestUserOnlyMessages(conversationId, userId, maxTurns);
    
    // 2. cutoffId = 保留原文的最早消息ID（超过此ID的消息需要被摘要）
    String cutoffId = resolveCutoffId(latestUserTurns);
    
    // 3. afterId = 上次摘要结束的消息ID（增量起点）
    String afterId = resolveSummaryStartId(conversationId, userId, latestSummary);
    
    // 4. 区间 [afterId, cutoffId] 内的消息需要被摘要
    List<ConversationMessageDO> toSummarize = conversationGroupService
            .listMessagesBetweenIds(conversationId, userId, afterId, cutoffId);
}
```

**示意图**：

```
时间线 →  消息1  消息2  消息3  消息4  消息5  消息6  消息7  消息8
              │      │      │      │      │      │      │      │
              ▼      ▼      ▼      ▼      ▼      ▼      ▼      ▼
         ┌───────────────────────────────┐   ┌───────────┐
         │   需要被摘要的历史消息         │   │ 保留原文  │
         │   [afterId, cutoffId]        │   │ last 4    │
         └───────────────────────────────┘   └───────────┘
                   │                                  │
                   ▼                                  ▼
              生成摘要                           直接保留
                   │                                  │
                   └──────────┬───────────────────────┘
                              ▼
              最终上下文 = [摘要(系统消息) + 最新4轮原文]
```

### 3.4 LLM 摘要生成

```java
private String summarizeMessages(List<ConversationMessageDO> messages, String existingSummary) {
    List<ChatMessage> summaryMessages = new ArrayList<>();
    
    // 1. 系统提示词
    String summaryPrompt = promptTemplateLoader.render(CONVERSATION_SUMMARY_PROMPT_PATH, ...);
    summaryMessages.add(ChatMessage.system(summaryPrompt));
    
    // 2. 历史摘要（用于增量合并）
    if (StrUtil.isNotBlank(existingSummary)) {
        summaryMessages.add(ChatMessage.assistant(
            "历史摘要（仅用于合并去重，不得作为事实新增来源；若与本轮对话冲突，以本轮对话为准）：\n"
            + existingSummary.trim()
        ));
    }
    
    // 3. 待摘要的消息列表
    summaryMessages.addAll(histories);
    
    // 4. 用户指令
    summaryMessages.add(ChatMessage.user(
        "合并以上对话与历史摘要，去重后输出更新摘要。要求：严格≤" + summaryMaxChars + "字符；仅一行。"
    ));
    
    // 调用 LLM
    ChatRequest request = ChatRequest.builder()
            .messages(summaryMessages)
            .temperature(0.3D)  // 低温度保证稳定性
            .topP(0.9D)
            .build();
    return llmService.chat(request);
}
```

## 四、当前设计优缺点分析

### 4.1 优点

| 优点 | 说明 |
|------|------|
| **增量摘要** | 每次只处理新增消息，避免全量重算，节省 Token |
| **异步执行** | 摘要生成在独立线程池执行，不阻塞对话响应 |
| **分布式锁** | 使用 Redisson 锁防止多节点并发重复摘要 |
| **优雅降级** | 各环节失败时有 fallback，不影响主流程 |
| **配置灵活** | 轮数阈值、摘要长度等均可配置 |
| **分层设计** | 接口与实现分离，便于扩展 |
| **并行加载** | 摘要和历史并行加载，提升响应速度 |

### 4.2 缺点

| 缺点 | 影响 | 代码位置 |
|------|------|----------|
| **压缩时机单一** | 仅在 assistant 回复后触发，无法主动触发 | `compressIfNeeded()` |
| **摘要内容不可控** | 完全依赖 LLM，可能丢失关键信息 | `summarizeMessages()` |
| **无摘要质量评估** | 无法判断摘要是否准确完整 | 缺失 |
| **无缓存机制** | 每次 load 都查询数据库 | `loadHistory()` |
| **摘要冲突处理** | 仅提示"以本轮为准"，无强制冲突解决 | 提示词中 |
| **无手动压缩接口** | 无法按需触发压缩 | 缺失 |
| **锁粒度较粗** | 整个会话加锁，并发写入可能阻塞 | `SUMMARY_LOCK_PREFIX` |

### 5.2 引入摘要缓存

**问题**：每次加载都查询数据库，性能开销大

**方案**：

```java
public class CachedConversationMemoryStore implements ConversationMemoryStore {
    
    private final RedisTemplate<String, Object> redisTemplate;
    private static final String HISTORY_CACHE_PREFIX = "ragent:memory:history:";
    private static final int CACHE_TTL_MINUTES = 30;
    
    @Override
    public List<ChatMessage> loadHistory(String conversationId, String userId) {
        String cacheKey = HISTORY_CACHE_PREFIX + userId + ":" + conversationId;
        
        // 先查缓存
        List<ChatMessage> cached = getFromCache(cacheKey);
        if (cached != null) {
            return cached;
        }
        
        // 查数据库
        List<ChatMessage> result = delegate.loadHistory(conversationId, userId);
        
        // 写入缓存
        cacheResult(cacheKey, result);
        
        return result;
    }
    
    @Override
    public void append(String conversationId, String userId, ChatMessage message) {
        String messageId = delegate.append(conversationId, userId, message);
        // 追加时异步刷新缓存
        refreshCacheAsync(conversationId, userId);
        return messageId;
    }
}
```

### 5.6 锁优化

**问题**：当前锁粒度为整个会话，并发写入时可能阻塞

**方案**：

```java
public class OptimisticLockSummaryService extends JdbcConversationMemorySummaryService {
    
    @Override
    private void doCompressIfNeeded(String conversationId, String userId) {
        // 使用乐观锁 + CAS 更新
        int retryCount = 0;
        while (retryCount < MAX_RETRIES) {
            // 1. 获取当前状态
            ConversationSummaryDO current = conversationGroupService
                    .findLatestSummary(conversationId, userId);
            long currentVersion = current != null ? current.getVersion() : 0;
            
            // 2. 计算摘要
            String newSummary = calculateSummary(conversationId, userId, current);
            
            // 3. CAS 更新
            boolean success = conversationGroupService.updateSummaryWithVersion(
                    conversationId, userId, newSummary, currentVersion);
            
            if (success) {
                return;
            }
            
            retryCount++;
            Thread.sleep(RETRY_DELAY_MS);
        }
        
        log.warn("摘要更新失败，已达最大重试次数");
    }
}
```

## 六、总结

| 维度 | 现状 | 改进方向 |
|------|------|----------|
| **存储** | JDBC 直读 | 引入 Redis 缓存层 |
| **触发** | 仅 assistant 回复后 | 支持手动触发 + 定时触发 |
| **压缩** | 固定阈值 | 动态自适应策略 |
| **质量** | 无评估 | 引入质量评分机制 |
| **冲突** | 提示词层面 | 主动检测与解决 |
| **锁** | 分布式锁 | 乐观锁 + CAS |

记忆模块的核心价值在于**在有限的上下文窗口内保留尽可能多的有效信息**。当前实现已经具备了基本的增量压缩能力，但在性能优化、质量控制和灵活性方面仍有提升空间。建议根据实际业务场景选择合适的改进方案，优先实施缓存和质量评估功能。

# 对话记忆压缩流程演示

## 概述

本文档演示 Ragent 对话记忆模块如何处理从第1轮到第35轮的对话历史，展示压缩机制的工作原理和输出结果。

### 项目配置

```yaml
rag:
  memory:
    history-keep-turns: 4      # 保留最近4轮原始对话
    summary-start-turns: 5     # 从第5轮开始触发压缩
    summary-enabled: true      # 启用摘要功能
    summary-max-chars: 200     # 摘要最大200字符
```

### 压缩策略

| 轮数范围 | 处理方式 | 说明 |
|----------|----------|------|
| 1-4轮 | 保留原文 | 未达压缩阈值 |
| 5-8轮 | 第5轮触发压缩 | 摘要消息1-4，保留5-8 |
| 9-12轮 | 第9轮触发压缩 | 摘要消息5-8，保留9-12 |
| 13-16轮 | 第13轮触发压缩 | 摘要消息9-12，保留13-16 |
| ... | ... | ... |
| 33-35轮 | 第33轮触发压缩 | 摘要消息29-32，保留33-35 |

**用户**：你好，我想了解一下 Ragent 项目的主要功能。

### 第3轮：记忆模块询问

**用户**：记忆模块是如何工作的？

**助手**：记忆模块采用混合存储策略：
1. **历史对话**：保留最近N轮原始对话（默认4轮）
2. **摘要压缩**：对历史对话进行摘要，减少Token消耗
3. **增量摘要**：只对新增消息做摘要，避免全量重算
4. **异步执行**：摘要生成不阻塞主对话流程

### 第5轮压缩详情

**压缩前状态**：
- 原始消息：消息1-4（8条）
- 摘要：无
- 总消息数：8

**压缩过程**：
```java
// 1. 检测到第5轮assistant消息
if (message.getRole() == ASSISTANT && countUserMessages() >= 5) {
    // 2. 计算压缩区间
    cutoffId = messageIdOf(4轮);  // 保留4轮
    afterId = null;  // 首次压缩
    
    // 3. 获取待摘要消息
    toSummarize = messages[1-4];
    
    // 4. 调用LLM生成摘要
    summary = llmService.chat([
        system: "总结对话，≤200字符",
        user: "项目介绍、技术栈、记忆模块、部署方式"
    ]);
    // 结果：Ragent是RAG系统，支持文档上传、多通道检索、流式对话、意图识别。技术栈：Java+SpringBoot、PostgreSQL+Milvus、Redis、RocketMQ。记忆模块混合存储，异步摘要。支持Docker部署。
}
```

**压缩后状态**：
- 摘要消息：1条（系统消息）
- 原始消息：消息5-8（8条）
- 总消息数：9

### 第9轮压缩详情

**压缩前状态**：
- 摘要：摘要1（消息1-4）
- 原始消息：消息5-8（8条）
- 总消息数：9

**压缩过程**：
```java
// 1. 检测到第9轮assistant消息
if (message.getRole() == ASSISTANT && countUserMessages() >= 9) {
    // 2. 计算压缩区间
    cutoffId = messageIdOf(8轮);  // 保留4轮
    afterId = lastMessageIdOf(摘要1);  // 从上次摘要结束点开始
    
    // 3. 获取待摘要消息
    toSummarize = messages[5-8];
    
    // 4. 调用LLM生成摘要（增量合并）
    summary = llmService.chat([
        system: "总结对话，≤200字符",
        assistant: "历史摘要：Ragent是RAG系统，支持文档上传、多通道检索、流式对话、意图识别。技术栈：Java+SpringBoot、PostgreSQL+Milvus、Redis、RocketMQ。记忆模块混合存储，异步摘要。支持Docker部署。",
```

## 总结

通过35轮对话的压缩演示，可以看到Ragent记忆模块的工作机制：

1. **智能压缩**：从第5轮开始，每4轮触发一次压缩
2. **增量摘要**：每次只对新增消息做摘要，避免重复计算
3. **上下文保留**：保留最近4轮原始对话，保证对话连贯性
4. **Token优化**：35轮对话从~12,600 Token降至~1,450 Token，节省88%
5. **用户体验**：异步执行不阻塞响应，分布式锁保证一致性

这种设计在保证对话质量的同时，有效控制了上下文窗口大小，为长对话场景提供了可靠的解决方案。
